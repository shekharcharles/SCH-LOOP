# Project-local capability packs (S4)

**Status:** Approved design, not yet implemented
**Date:** 2026-08-05
**Depends on:** M6 contained worker execution (merged), the skill registry, the
supervised runner
**Blocks:** nothing — S2 and S3 do not depend on this

---

## 1. Why this exists

A worker is a real `claude -p` process. SCH already chooses which skills are
relevant and injects excerpts of them into the prompt — bounded, hashed and
recorded (`runner.mjs:532`). What SCH does **not** control is that the same
process independently loads the operator's entire global skill catalogue into its
own skill tool.

On this machine that is 38 user skills plus every installed plugin, on top of
SCH's curated selection. The result is the pain named in the product brief:
context spent on irrelevant instructions, several planning methodologies each
claiming to own the workflow, ambiguous tool selection, and cross-project
contamination that no amount of prompt discipline can reach.

This milestone gives each task its own capability pack and takes the global
catalogue away from the worker.

### Verified before designing

Every mechanism below was probed against the installed CLI rather than assumed.

| Question | Answer | How |
|---|---|---|
| Can a directory outside the repo supply skills? | Yes — `--plugin-dir <path>`, skills appear namespaced `<plugin>:<skill>` | probe listed `sch-probe:zzz-probe-marker` |
| Does that suppress the operator's global skills? | Yes, with `--setting-sources project` — all 38 gone, plugins too | probe listed no `gsap`, `taste-skill`, `superpowers`, `brandkit` |
| Do Anthropic's built-in skills survive? | Yes — 12 of them, including `schedule` and `loop`, which create persistent and recurring work | probe listing |
| Can an individual built-in be blocked? | **Invocation yes**, listing no — `--disallowed-tools "Skill(init)"` returns *"Skill execution blocked by permission rules"* | direct invocation probe |
| Is `--bare` usable? | **No.** It forces auth to `ANTHROPIC_API_KEY` and would break subscription/OAuth login | `claude --help` |
| Can a plugin carry executable hooks? | Yes — the installed `caveman` plugin registers `SessionStart` and `UserPromptSubmit` command hooks | its `plugin.json` |

That last row is the reason §3 generates a manifest rather than copying one.

## 2. Scope, as a claim and a non-claim

**Claimed after this milestone:**

- A worker cannot see or invoke any skill or plugin installed in the operator's
  global configuration.
- A worker can invoke exactly the skills SCH approved for that task, and those
  arrive as real invocable skills rather than prompt text.
- A worker cannot invoke a built-in skill that persists state, mutates
  configuration, or schedules future work.
- No file is written into the managed repository to achieve any of this.

**Not claimed:**

- Built-in skill *names* still appear in the worker's skill listing. Blocking
  invocation does not remove them from the list, so roughly a dozen names remain
  as context cost. This is disclosed, not fixed.
- This is not isolation. It is capability scoping, and it inherits every M6
  caveat: workers are not OS-sandboxed, writes outside the worktree are neither
  prevented nor detected, and the network is unrestricted.

## 3. The pack

One pack per **task**, matching the worktree lifecycle exactly: created at claim,
reused by every attempt, removed when the worktree is removed.

```
<state-root>/packs/<project>/task-<n>/
├── .claude-plugin/plugin.json      generated by SCH
└── skills/<skill-id>/SKILL.md      copied, by content hash, from the approved registry
```

`<state-root>` is the same root M6 established for worktrees
(`%LOCALAPPDATA%\sch-loop` on Windows, `${XDG_STATE_HOME:-$HOME/.local/state}/sch-loop`
on POSIX), and the pack sits beside the worktree rather than inside it.

**Never inside the repository.** A generated `.claude/` in the worktree would be
an untracked file in the tree SCH is about to inspect — it would fight the
clean-tree gate and surface as `UNEXPECTED_FILE_CHANGE`, and excluding it through
git configuration would mutate the operator's repository and trip
`git_config_changed`. Keeping SCH's artifacts out of the worker's tree is the
same rule M6 settled, for the same reason.

### The manifest is generated, never inherited

A plugin manifest may register hooks that execute arbitrary commands. SCH writes:

```json
{ "name": "sch-<project>-task-<n>", "description": "SCH Loop capability pack." }
```

and nothing else. A source skill's hooks, scripts, executables and nested plugin
manifests are **not** copied into the pack, and each refusal is recorded in the
pack manifest record. A skill that is only meaningful with its scripts is a skill
this mechanism cannot carry — that is a limitation to report, not to work around.

### Provenance

Every skill copied into a pack is recorded with its id, source root, content hash
and the reason the recommendation engine chose it. The hash is re-verified at
copy time against the approved registry; a skill whose content moved since
approval is refused with `SKILL_HASH_STALE`, exactly as today.

## 4. How the worker is launched

```
--plugin-dir <pack>
--setting-sources project
--disallowed-tools Skill(<denied built-in>) ...
```

`--setting-sources project` is what removes the global catalogue. Because the
worker's cwd is the worktree and SCH writes no `.claude/` there, `project` names
a source that is empty — which is the intent.

### The built-in denylist

Built-ins are default-denied where they persist state, mutate configuration, or
schedule future work, and allowed where they only read or advise:

| Denied | Why |
|---|---|
| `schedule` | creates scheduled cloud agents — work outside SCH's queue and lease |
| `loop` | creates recurring execution — the same problem on a timer |
| `init` | writes `CLAUDE.md` into the repository |
| `update-config` | mutates `settings.json`, including permissions and hooks |
| `fewer-permission-prompts` | writes a permission allowlist |
| `run` | launches and drives the project's application |

| Allowed | Why |
|---|---|
| `dataviz`, `simplify`, `claude-api`, `review`, `security-review`, `keybindings-help` | read or advise only |

The list is **data**, versioned with the pack and overridable per project by an
operator — not a constant buried in the launcher. A built-in that appears in a
future CLI release and is not on either list is **denied**, and the pack record
says so: an unrecognised capability is not a safe one.

## 5. What the pack replaces

Today `selectSkills` injects up to 3000 characters of every chosen skill into
every prompt. That injection is itself a large part of the context cost this
milestone exists to reduce.

The split follows a distinction `skill-recommend` already draws:

- **Required** skills keep their injection. SCH guarantees they are in context.
  Making a required skill's loading depend on the model choosing to invoke it
  would invert this system's central rule — code owns the decision, the model
  owns bounded execution inside it.
- **Recommended** skills drop to a one-line index naming the skill, its purpose
  and its namespaced invocation id. They live in the pack and load on demand.

The prompt manifest records both, so the character saving is measurable rather
than asserted.

## 6. Failure modes

- **Pack missing or unreadable at claim** — `NEEDS_DECISION`, no worker starts.
  A worker launched without its pack would silently fall back to whatever the CLI
  finds, which is the failure this milestone exists to prevent.
- **A skill's hash moved since approval** — refused with `SKILL_HASH_STALE`,
  unchanged from today.
- **Zero approved skills for the task** — a valid pack with an empty `skills/`.
  The worker runs with allowed built-ins only, and the record says the pack was
  deliberately empty rather than that packing failed.
- **A source skill carries hooks or scripts** — copied without them, recorded.
- **`--plugin-dir` rejected by the CLI** — preflight failure, not a warning. The
  containment claim is void without it.

## 7. Verification

- A real worker's skill listing contains **no** globally installed skill. The
  probe form is proven: ask a worker to list its skills, assert absence.
- A pack skill is present and invocable under its `<plugin>:<skill>` id.
- A denied built-in returns *"Skill execution blocked by permission rules"* when
  invoked.
- Hooks present in a source skill do not appear in the generated manifest.
- A pack whose skill content was altered after approval is refused.
- Prompt character count for a recommended-only task is lower than today's, by a
  recorded amount.
- **Known gap, asserted:** built-in skill names still appear in the listing. If
  that assertion ever fails because they stopped appearing, the residual in §2 is
  closed and the documentation must be corrected.

## 8. Out of scope

The operator's own interactive session. When a person opens Claude Code
themselves, they carry their global catalogue; this milestone governs worker
processes only, and no worker flag can change what a human's session loads.

Also out of scope: conflict detection between overlapping methodologies, the
capability compiler's scoring model, and any change to which skills
`skill-recommend` chooses. This milestone changes how the chosen set reaches the
worker, not how it is chosen.
