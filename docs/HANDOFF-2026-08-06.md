## How to finish, in order

Identify each finished branch by its last commit subject:
`git log -1 --format=%s <branch>`. A branch still at
"merge(m10): a retry runs the repairer" has not delivered yet.

Merge order — lowest risk first, scheduler-touching LAST:

1. **Network restriction** (subject will mention network/proxy/policy) — verify
   its README wording never says "blocked" unless literally true, run its test
   file, merge.
2. **OS sandboxing** (job objects / containment evaluation) — a negative result
   with evidence is an acceptable deliverable. Same check on wording.
3. **Knowledge ingestion** (bounded, hashed knowledge index) — run its tests;
   check it respects the character budget and reuses the runner's REDACTIONS.
4. **Distributed worker seam** (loopback executor + ADR) — check the ADR labels
   unproven things unproven; credentials must never widen.
5. **SQLite state authority** — read its report FIRST. If it delivered the
   "dual-write, JSON authoritative" fallback, that is fine — merge it. If it
   claims full migration, verify `tests/state-concurrency.test.mjs` still passes
   and that a `state.json` import path exists with the JSON kept as backup.
6. **Template phase order** — heaviest. Verify tests/scheduler.test.mjs,
   tests/phases.test.mjs, tests/semantic.test.mjs, tests/outcome.test.mjs all
   pass in ITS worktree before merging.

Per merge: `git merge --no-ff <branch>`, resolve LESSONS.md conflicts by UNION
(keep both sides' bullet lines, drop markers), run `npm run validate`, run the
branch's own test files, `node scripts/secret-scan.mjs --staged`, push main.
