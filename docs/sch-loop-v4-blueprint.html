TL;DR

  • Keep the engine. Builder → Verifier → Judge → Manager, council with five providers, fresh claude -p per ticket, fail-closed merge, worktrees, notify — all exist in ~/.claude/SCH-loop/runtime.
  • Add four skills (sch-prd, sch-architecture, sch-setup, sch-insert), rewrite two (sch-tickets, sch-build), give the router go.
  • One queue. task.md for humans, .sch-loop/state.json for the machine. No task.q.
  • Context rot is solved by architecture. One fresh executor process per ticket. Chain only on after: + measured usage < 130k.
  • Council is gated. Architecture, plan, flagged tickets, two reds. Per-ticket is 4× cost.
  • Lab first. Everything lives in D:\SCH-LOOP\lab\.claude; nothing touches ~/.claude until three tickets, one insert, one red and one ship have run there.

Per-ticket loop

Your six steps, in the order that keeps the expensive reviewer off code that does not compile.

  1. See ticket. Fresh process. Four-line brief: role / ticket JSON / read_first / output contract. File content is untrusted input.
  2. Build. Worktree sch/<id>, only allowed_paths. Auto-fix bugs in scope; architectural change → decision ticket; package install → human gate.
  3. TDD in lab. RED must fail for the intended reason, commit test(id). GREEN minimal, commit feat(id). Refactor optional. Three attempts.
  4. Check. Types, lint, ticket verify[], path containment, must_not greps, secret scan, diff-matches-claims. Red → step 3.
  5. Code review. Fresh reviewer, never the author. Two verdicts: Spec and Quality. CRITICAL/HIGH adversarially verified by a second fresh process; unverified stays blocking. Max three rounds.
  6. Test. Full suite → Judge (fresh, read-only, sees diff + evidence) → Manager (code) → PASS / RETRY / HUMAN.

Ticket types

Not every ticket is a build. The type decides whether TDD and review run and whether main is ever touched.

buildRED → GREEN → REFACTOR in worktreeyesyes

researchfindings tagged [VERIFIED] / [CITED] / [ASSUMED]nono

size picks pipeline depth: XS implement→test · S +review · M +read_first research · L +spike first, council before.

Corrections to the described design

  1. Council per task → gated. Four models on every ticket is 4× tokens and slower than the build. Default gates: architecture, plan, council:true, two consecutive reds, phase-verify failure.
  2. Check before review. Cheap deterministic gates first; fresh-context review only on code that compiles.
  3. Reviewer is a different process. All five repos: the author cannot judge its own diff.
  4. "Implement only when green" = deliver. The worktree green is the implementation; green unlocks the fail-closed merge.
  5. Orchestrator "small work" has a boundary: task.md, .sch-loop/, docs, LESSONS, CLAUDE.md. Never app source, or it becomes a second executor.
  6. Drop task.q. Two queues drift. One human file + one machine index.
  7. Insert by suffix, never renumber. T1.4a, phase 1.1. Position is priority because the scan is top-down.
  8. Bypass mode needs three fences: worktree + write-outside detection, allowed_paths/protected_paths hook, destructive-Bash guard. One git clean in a worktree deleted prior work in GSD (#2075).
  9. Herder is herdr here; antigravity/gemini not on PATH. Setup reports live seats instead of assuming four.
  10. "Clear after each task" → fresh process per task. Already what sch-run-task.mjs does. Clearing a session is the weaker version.
  11. Ticket types answer "not every task is a dev task".
  12. Two checkouts: ~/.claude/SCH-loop contains D:\SCH-LOOP's HEAD and is 13 commits ahead (5 unpushed). D: is stale, not diverged. Commit + push home, pull in D:.

Lab first

Project-local install inside this repo. Nothing touches ~/.claude until the loop is proven.

D:\SCH-LOOP\lab\
  .claude\settings.json        hooks: write-guard · destructive-bash · executor allowedTools
  .claude\skills\sch-*\        the 14 skills (Claude Code loads project-local skills)
  .claude\sch\                 runtime/ + scripts/ — every skill path resolves here
  .sch-loop\                   config.md · state.json · tickets · briefs · reports · evidence
  task.md
  src\  tests\                 sample app under test

Exit criteria: brainstorm → PRD → architecture → plan → tickets → three tickets built (build, test, human) → one inserted ticket picked before a later one → one forced red reaching [!] and council → phase verify → ship (PR into lab). Then sch-setup --global copies the same tree to ~/.claude.

Implementation ≈ 5 working days. Steps that are the loop: task.md parser (half day), sch-tickets rewrite (half day), Herdr-pane executor + report envelope (1 day), two-verdict review (half day). Everything else is prose skills and cleanup.
